## Defect 1: Fabricated Agent Output (HIGH)

**Location**: Lines 212-219 (Month-End Close worked example, Day 3: Bank reconciliation)

**Issue**: The lesson presents a specific reconciliation output table as if it is what Claude *will* produce when the student runs `/reconciliation bank-USD 2025-03`. The table shows exact items, categories, amounts ($2,180 timing differences, $840 bank charges, $400 unidentified deposit), and action-required text.

```
| Item                                        | Category                   | Amount | Action Required              |
| ------------------------------------------- | -------------------------- | ------ | ---------------------------- |
| 4 checks issued in March, clearing in April | Timing difference          | $2,180 | None -- resolves next period |
| 2 bank service charges not posted to GL     | Error requiring correction | $840   | Journal entry needed         |
| 1 unidentified deposit                      | Requires investigation     | $400   | Research before Day 5        |
```

This is fabricated output -- it was not generated by running the command. The student's actual output will differ because the practice data is generated dynamically by Claude (the "Prepare Your Practice Data" section asks Claude to create data with specific parameters). The worked example presents a fictional run as if it were deterministic.

**Recommendation**: Convert this table to an "intent table" format that describes the *type* of output to expect rather than fabricating exact values. For example: "The reconciliation output will categorise each discrepancy as a timing difference, an error requiring correction, or an item requiring investigation, and recommend an action for each."

## Defect 2: Inline Data Injection (MEDIUM)

**Location**: Lines 139-154 (Prepare Your Practice Data prompt)

**Issue**: The prompt injects specific financial data directly into the prompt text:

- "45 transactions -- deposits totalling $892,000 and withdrawals totalling $876,580"
- "$3,420 discrepancy against the bank statement"
- "Q1 revenue of $465K against a $500K budget, broken down by three product lines"

This is inline data injection -- the lesson embeds specific dollar amounts and transaction counts directly inside the prompt rather than referencing an external data source or letting the exercise use whatever data the student has. While this particular case is defensible (the prompt asks Claude to *generate* practice data, so the numbers are parameters, not assertions), the problem is that these exact numbers then cascade through the worked example (the $3,420 discrepancy reappears on line 206 and in the reconciliation table) creating a tight coupling between the data-generation prompt and the fabricated output.

**Recommendation**: Either (a) keep the data-generation prompt but decouple the worked example from its specific values (use intent descriptions instead of exact amounts), or (b) provide the practice data as downloadable files with known values, and base the worked example on those files. Approach (a) is simpler.

## Defect 3: Narrative Referencing Fabricated Content (MEDIUM)

**Location**: Lines 226-228 (Day 4: Correcting entries)

**Issue**: The narrative after the fabricated reconciliation table continues to reference fabricated output as if it were real:

> "Claude generates the entry: debit Bank Charges Expense $840, credit Cash -- USD Operating $840, with transaction references and a note that this entry requires controller review before posting."

This presents a specific journal entry with exact dollar amounts ($840) that were fabricated in the reconciliation table. The student's actual journal entry output will depend on whatever data Claude generated in the practice data step. The lesson treats a fabricated chain of outputs as deterministic.

Similarly, line 236: "The CFO wants to know why revenue is $35K below budget" -- this $35K figure ($500K budget - $465K actual) comes from the data-generation prompt parameters but is presented as a discovered insight from running `/variance-analysis`.

**Recommendation**: Reframe these as descriptions of the *type* of output rather than exact values. For example: "Claude generates a journal entry with debits and credits matching the error amount identified in the reconciliation, along with transaction references and a review note."

## Defects NOT Found

### 2. Missing Skill Names
No prompts in the lesson require skill invocation by name. The Try With AI prompts are general-purpose educational prompts, not plugin-specific workflows. The exercises correctly use command names (`/reconciliation`, `/journal-entry`, etc.) which are commands, not skills. Skills are correctly described as passive/auto-activating. No defect.

### 4. Fiction-Researching Prompts
All three Try With AI prompts ask Claude to explain concepts or walk through workflows. None ask Claude to "research" or "look up" fictional products, fictional companies, or fictional data. Prompt 3 provides inline data for a reconciliation exercise, which is appropriate (it's asking for analysis of a hypothetical scenario, not research of a fictional entity). No defect.

### 6. Terminology Issues
The lesson correctly uses "Cowork" throughout (not "Claude in Excel" for Cowork contexts). The one reference to "Claude in Excel" (lines 108, 110, etc.) correctly refers to the separate Claude in Excel product from Lessons 1-3, which is the intended usage per `.claude/rules/cowork-content.md`. The title "Cowork Finance Plugins" is correct. Skill invocation terminology (passive activation vs explicit `/command`) is correct. No defect.

## Overall Assessment

The lesson has **1 high-severity** and **2 medium-severity** defects, all related to the fabricated output pattern. The worked example (lines 200-254) presents a fictional run of the month-end close workflow with specific dollar amounts as if they were deterministic outputs. This creates two problems:

1. **Student confusion**: When the student runs the same commands, they will get different numbers (since the practice data is dynamically generated), potentially making them think something went wrong.

2. **Tight coupling**: The data-generation prompt parameters ($3,420 discrepancy, $892K deposits, etc.) are hard-coded to match the fabricated worked example. If either changes independently, the lesson becomes internally inconsistent.

The fix is consistent: convert fabricated output tables and narrative references to intent descriptions that explain what *kind* of output to expect, rather than fabricating exact values.
